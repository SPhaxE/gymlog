# mock/ 说明

阶段 2 的真实文案与示例数据。页面和测试只从这里取数，不写占位文字。

| 文件 | 内容 | 生成方式 |
|---|---|---|
| `exercises.json` | 动作库 154 个（含要领文案、示范媒体路径） | 手工整理，见 `docs/asset-audit.md` |
| `muscles.json` | 6 个肌群、32 个肌头、三档肌群的基础恢复窗口与容量系数 | 手工整理 |
| `history.json` | 示例训练历史：29 次训练、8 周、每周 3–4 次 | `python3 scripts/gen_mock.py`（固定种子，可重复生成） |
| `profile.json` | 默认档案（进阶 · 60 分钟）与高阶档案（90 分钟）；器械目录 | 同上 |
| `scenarios.json` | 各页面状态怎么从上面几份数据构造出来 | 同上 |

**不要手改 `history.json`、`profile.json`、`scenarios.json`**：改 `scripts/gen_mock.py` 后重新生成。脚本带断言，会拦住「减量信号丢了」「最近一次卧推不再是 PR」这类退化。

## 数据约定

- **日期**：`daysAgo`（0 = 今天）加 `startTime`。演示数据载入时换算成真实日期，所以「近 7 天」永远有数据。排布按「今天是周六」。
- **组类型**：`warmup` 不计入容量、趋势和 PR；`work` 和 `drop` 计入。
- **单侧动作**：`exercise.unilateral = true` 的动作，每组记 `repsLeft` / `repsRight`，其余动作记 `reps`。`unilateral` 的含义是「一次只练一侧」，当前 154 个动作里只有 10 个是（此前从 V1 带来的标记有 58 个，大半不符合这个定义，已重新核定）。
- **力竭度** `exertion`：1–10，`null` 表示跳过。**RPE** `rpe`：1–10，步进 0.5，`null` 表示没记。
- **预估 1RM**：取一次训练里该动作所有工作组（含递减组）的最大值，Epley 与 Brzycki 取均值；PR = 该动作预估 1RM 创历史新高，该动作的第一次记录是基线，不算 PR。

## 示例历史里埋的情形

| 情形 | 在哪里 | 用来验证 |
|---|---|---|
| 减量信号 | 杠铃深蹲、杠铃直腿硬拉：最近 3 周预估 1RM 连续下降，每次 > 1% | 引擎的减量触发；P01「建议本周减量」 |
| 最近一次 PR | `demo-w0-push`：杠铃卧推（以及另外几个动作）创新高 | P05 有 PR；P07 PR 角标 |
| 新动作（只有 1 次记录） | 哑铃保加利亚分腿蹲（`demo-w0-lowerB`，单侧） | P05 基线；P10「再练一次就能看到趋势」 |
| 只有 2 次记录 | 绳索面拉（`demo-w1-pull`、`demo-w0-pull`） | P10 刚好能画线 |
| 有未做的动作 | `demo-w3-pull` 的哑铃锤式弯举 | P05 部分未做；P08 |
| 首次训练 | `demo-w7-lowerA` | P05 首次记录，作为基线 |
| 热身组 / 递减组 | 每次训练的第一个复合动作有 2 组热身；`demo-w4-push` 卧推末尾有一组递减组 | 热身不计入；递减计入 |
| 没记 RPE / 没填力竭度 | 部分训练 RPE 全空；`demo-w5-pull` 力竭度为 `null` | 可选字段的空态 |
| 从未练过的肌头 | 32 个肌头里有 6 个整段历史都没练到（如下背部、胫骨前肌） | P06「从未练过：不显示恢复度」 |
| 条数多于一页 | 29 条，超过 P07 分段加载的页大小（暂定 20，阶段 5 定） | P07 分段加载 |

PR 角标在 29 次训练里出现在 17 次——因为一次训练有 5 个动作，只要有一个创新高就算。这是示例数据的特点，不代表真实用户的比例。

## 已知局限

- 「恢复日」场景的具体数字（各肌头恢复度、还需几小时）取决于引擎实现，场景只保证「几乎所有肌头今天刚被练过且力竭度为 10」，数字在阶段 5 用引擎测试固定。
- `scenarios.json` 里的 `appState` 字段名是暂定的，等阶段 5 的 store 定下来再对齐。
- MVP 动作库里没有壶铃、弹力带、杠铃片的动作，档案里这三项（`inPool: false`）勾选了也不会改变处方。
